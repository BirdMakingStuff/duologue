## I Have a Question

> If you want to ask a question, we assume that you have read the available [documentation](README.md).

Before you ask a question, it is best to search for existing [Issues](https://github.com/BirdMakingStuff/duologue/issues) that might help you. In case you have found a suitable issue and still need clarification, you can write your question in this issue. It is also advisable to search the internet for answers first.

If you then still feel the need to ask a question and need clarification, we recommend the following:

- Open an [Issue](https://github.com/BirdMakingStuff/duologue/issues/new).
- Provide as much context as you can about what you're running into.
- Provide project and platform versions (nodejs, npm, etc), depending on what seems relevant.

We will then take care of the issue as soon as possible.

### Generative AI Policy
#### Usage for requests and issues
- It is in everyone's best interest to **not** submit issues, pull requests or feature requests that are AI-generated.
- All such requests will be closed and submitters will be blocked from the repository.

#### You must...
- Be able to understand and respond to questions relating to the issue or the fix you provide.
- You *can* use an AI tool for proofreading, translating or understanding the issue's content.
- You **cannot** use AI tools to generate the issue text, or the issue itself.

#### Pull Requests
- You should be able to explain every part of the code you have written/modified in your PR.
- If you do not understand your PR, **do not** submit it. You cannot use an AI tool to generate code for you.

The rationale behind this policy is that automated contributions are a waste of the maintainers' time. Humans spend their time and brainpower reviewing every submission. Issues or pull requests generated by automation tools create an imbalance of effort between the submitter and the reviewer. Nobody learns anything when a maintainer reviews code written by an LLM.

Additionally, such AI-generated content impedes legitimate issues and feature requests that would add more value to the project.

### Your First Code Contribution

If you are new to the project, start by looking through open issues for work marked as suitable for contributors. Before starting significant work, leave a comment on the issue describing your proposed approach so that the maintainers can confirm that the change fits the project.

For a code contribution:

- Fork the repository and clone your fork.
- Create a focused branch from the default branch, such as `fix-command-error` or `add-thread-filter`.
- Keep each change focused. Avoid mixing unrelated refactors, formatting changes, or dependency updates into a feature or bug fix.
- Do not commit credentials, `config.toml`, `.env` files, runtime data, or generated `dist` output.
- Explain any behavior that is difficult to understand with a short code comment, and update the README when user-facing behavior changes.

### Development Setup

Duologue is written in TypeScript and targets Node.js 24, which is also the version used by the Docker image. npm is the supported package manager.

1. Fork and clone the repository, then move into the project directory.
2. Install dependencies:

   ```bash
   npm ci
   ```

3. Create a local configuration file:

   ```bash
   cp config.toml.example config.toml
   ```

   Fill in the Discord bot token and application client ID. Add the Ed Discussion tokens and allowed course IDs needed for your test server. Keep this file local; it is ignored by Git.

4. Build the project to check the TypeScript compilation:

   ```bash
   npm run build
   ```

5. Run the bot directly from TypeScript during development:

   ```bash
   npm run dev
   ```

The bot needs a valid Discord application and configuration to start. To refresh the slash commands for a configured application, run `npm run commands`. This updates the application commands globally, so only run it when you intend to change the commands registered for that application.

The Docker development setup is also available when you want to test the container image:

```bash
docker compose -f docker-compose.dev.yml up --build
```

### Validation

There is currently no automated test suite. Every code change should at least pass `npm run build`. For changes that affect Discord commands, polling, configuration, or persistence, test the relevant behavior in a development Discord server and describe the result in the pull request.


### Reporting Bugs

<!-- omit in toc -->
#### Before Submitting a Bug Report

A good bug report shouldn't leave others needing to chase you up for more information. Therefore, we ask you to investigate carefully, collect information and describe the issue in detail in your report. Please complete the following steps in advance to help us fix any potential bug as fast as possible.

- Make sure that you are using the latest version.
- Determine if your bug is really a bug and not an error on your side e.g. using incompatible environment components/versions (Make sure that you have read the [documentation](README.md). If you are looking for support, you might want to check [this section](#i-have-a-question)).
- To see if other users have experienced (and potentially already solved) the same issue you are having, check if there is not already a bug report existing for your bug or error in the [bug tracker](https://github.com/BirdMakingStuff/duologue/issues?q=label%3Abug).
- Also make sure to search the internet (including Stack Overflow) to see if users outside of the GitHub community have discussed the issue.
- Collect information about the bug:
  - Stack trace (Traceback)
  - OS, Platform and Version (Windows, Linux, macOS, x86, ARM)
  - Version of the interpreter, compiler, SDK, runtime environment, package manager, depending on what seems relevant.
  - Possibly your input and the output
  - Can you reliably reproduce the issue? And can you also reproduce it with older versions?

<!-- omit in toc -->
#### How Do I Submit a Good Bug Report?

> You must never report security related issues, vulnerabilities or bugs including sensitive information to the issue tracker, or elsewhere in public. Instead sensitive bugs must be sent by email to <hello@birdmakingstuff.nz>.
<!-- You may add a PGP key to allow the messages to be sent encrypted as well. -->

We use GitHub issues to track bugs and errors. If you run into an issue with the project:

- Open an [Issue](https://github.com/BirdMakingStuff/duologue/issues/new). (Since we can't be sure at this point whether it is a bug or not, we ask you not to talk about a bug yet and not to label the issue.)
- Explain the behavior you would expect and the actual behavior.
- Please provide as much context as possible and describe the *reproduction steps* that someone else can follow to recreate the issue on their own. This usually includes your code. For good bug reports you should isolate the problem and create a reduced test case.
- Provide the information you collected in the previous section.

Once it's filed:

- The project team will label the issue accordingly.
- A team member will try to reproduce the issue with your provided steps. If there are no reproduction steps or no obvious way to reproduce the issue, the team will ask you for those steps and mark the issue as `needs-repro`. Bugs with the `needs-repro` tag will not be addressed until they are reproduced.
- If the team is able to reproduce the issue, it will be marked `needs-fix`, as well as possibly other tags (such as `critical`), and the issue will be left to be [implemented by someone](#your-first-code-contribution).

### Suggesting Enhancements

This section guides you through submitting an enhancement suggestion for Duologue, **including completely new features and minor improvements to existing functionality**. Following these guidelines will help maintainers and the community to understand your suggestion and find related suggestions.

<!-- omit in toc -->
#### Before Submitting an Enhancement

- Make sure that you are using the latest version.
- Read the README carefully and find out if the functionality is already covered, maybe by an individual configuration.
- Perform a [search](https://github.com/BirdMakingStuff/duologue/issues) to see if the enhancement has already been suggested. If it has, add a comment to the existing issue instead of opening a new one.
- Find out whether your idea fits with the scope and aims of the project. It's up to you to make a strong case to convince the project's developers of the merits of this feature. Keep in mind that we want features that will be useful to the majority of our users and not just a small subset. If you're just targeting a minority of users, consider writing an add-on/plugin library.

<!-- omit in toc -->
#### How Do I Submit a Good Enhancement Suggestion?

Enhancement suggestions are tracked as [GitHub issues](https://github.com/BirdMakingStuff/duologue/issues).

- Use a **clear and descriptive title** for the issue to identify the suggestion.
- Provide a **step-by-step description of the suggested enhancement** in as many details as possible.
- **Describe the current behavior** and **explain which behavior you expected to see instead** and why. At this point you can also tell which alternatives do not work for you.
- You may want to **include screenshots or screen recordings** which help you demonstrate the steps or point out the part which the suggestion is related to. You can use [LICEcap](https://www.cockos.com/licecap/) to record GIFs on macOS and Windows, and the built-in [screen recorder in GNOME](https://help.gnome.org/users/gnome-help/stable/screen-shot-record.html.en) or [SimpleScreenRecorder](https://github.com/MaartenBaert/ssr) on Linux. <!-- this should only be included if the project has a GUI -->
- **Explain why this enhancement would be useful** to most Duologue users. You may also want to point out the other projects that solved it better and which could serve as inspiration.

### Improving The Documentation

Documentation improvements are welcome, including corrections, clearer setup steps, examples, and explanations of command behavior. Keep documentation accurate for the current code and configuration format. If a code change changes user-facing behavior, update the relevant section of [README.md](README.md) in the same pull request.

For small documentation fixes, open a pull request directly. For larger changes, open an issue first so the scope can be agreed on before work begins.

## Styleguides

### TypeScript and Code Style

- Follow the existing TypeScript structure and naming conventions.
- Use tabs for indentation in TypeScript files, single quotes for strings, and semicolons, as configured in `src/.eslintrc.json`.
- Prefer small, focused functions and explicit error handling.
- Use `.js` extensions in relative imports, as required by the repository's NodeNext TypeScript configuration.
- Do not add dependencies unless they are necessary and their maintenance and runtime cost are justified.

### Commit Messages

Write commit messages in the imperative mood and keep the subject concise. Use a subject that explains the change, for example:

```text
Handle missing Ed Discussion threads
```

Keep unrelated changes in separate commits. Dependency update commits should identify the dependency being updated.

### Pull Requests

Before opening a pull request:

- Rebase or update your branch from the current default branch.
- Run `npm run build` and confirm it succeeds.
- Test user-facing behavior that cannot be covered by the build, especially Discord commands and configuration changes.
- Update documentation and `config.toml.example` when applicable.
- Review the complete diff and remove debug logging, generated files, and secrets.

The pull request description should explain what changed, why it changed, how it was tested, and any setup or configuration needed to review it. Link the relevant issue when one exists. Keep the pull request focused and be prepared to explain every line you changed.

Maintainers may ask for changes, additional testing, or a smaller scope before merging. Do not force-push or rewrite commits after review without mentioning it in the pull request.
